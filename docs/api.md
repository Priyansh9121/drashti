# Drashti's local API (v1)

This document describes the local network API shipped in **1.0.0-alpha.22**, including screen geometry and video-caption state; since alpha.21 the skip command takes `back` and `forward` only, and since alpha.22 the engine state is version 32, with a video cue (an older client stops and says so). It also describes the video Shape map, received stream-link state, and the separate desktop bridges for video preparation and, since alpha.22, Prepare translations’ engine below. The paired controller uses the separate node link described below. Historical state changes say which versions introduced them. The desktop slide editor authors through its typed desktop bridge; it adds no HTTP authoring endpoint here.

**Desktop controls in alpha.20.** The [Drashti Manual](manual/start.md#using-this-manual) gives the operating steps. Media information, the Resume offer, A-B repeat, frame steps, Snapshot, playlist Find/timing/M3U, appearances, YouTube scheduling, QR downloads and sending the picture to other software do not add HTTP routes here. Existing Remote playback and audio-playlist actions keep their contracts below. [Report a Problem](manual/help.md#report-a-problem) uses the [access service](access-setup.md#11-putting-in-a-change-later-always-the-same-deployment); a node hands its report to Main. It is separate from the local v1 API.

Drashti answers on the mandir's local network, once the operator turns the network on (**Phones** in the header, Pro Mode). The phone remote, the stage display and the announcements page use this API; so can a script, or Bitfocus Companion's generic HTTP actions on a Stream Deck. It is loosely modelled on the network API of the presentation software Drashti replaces: actions are short paths such as `/trigger/next` and `/clear/slide`, but every request must carry a paired device's token.

Everything here is **local only**: requests are refused from addresses outside the private ranges, from a Host header that is not this computer's own address or name, and (from a browser) from pages that are not Drashti's own. See README, "The local network", for the security model.

**Not here: the node link.** Output nodes (Session 13: other computers running Drashti as a Node) talk to Main on a port of their own (8741) over TLS with Main's own certificate, which each node pins when it pairs. That link is for Drashti alone and is not part of this API: a script or Companion cannot use it, and it refuses browsers. See README, "Output nodes". A paired computer explicitly given **Shared show view** follows LIVE and NEXT over that same node link; Main can also allow show controls and media playback for that paired computer. Those use Main's ordinary action checks and add no HTTP endpoint.

**Import from a Link on the computer.** The operator’s desktop bridge checks a YouTube or Dropbox link for the small window, then Download supplies the edited name and chosen save folder. It saves and imports the media into the open playlist; Audio takes a YouTube video’s MP3. The remembered caption tick saves creator captions and the original automatic language as SRT files beside the media, plus a learning copy and `captions.json` in the chosen captions folder. Checks, downloads and captions wait on air or while recording. These desktop actions are handled by `links.look`, `links.pickFolder` (downloads or captions), `links.start` (name and captions options) and `links.view`; their detailed file contract is in README, “Import from a Link”.

**PDF mark clicks** (alpha.21). The desktop editor keeps each mark’s optional click order with its shape. Slide composition uses the existing deck motion timeline, so the existing Next and Back commands and state feed carry each mark’s step to screens, nodes and phones. There is no new HTTP authoring route. PDF copies show all visible marks together.

## Basics

- **Address:** `http://<computer>:8740` (the port is set in the Phones panel). Examples below use

  ```sh
  DRASHTI=http://192.168.1.20:8740
  TOKEN=…   # a paired Remote device's token (see "A token for a script")
  ```

- **Versions:** everything is under `/api/v1`. Within v1, fields and requests may be added, never changed or taken away; a change that breaks would come as `/api/v2`. The one exception is Session 55's (1.0.0-alpha.14), which took Props, Looks, masks, the logo and the idle rotation out of Drashti, and their requests with them: `/api/v1/props…`, `/looks…`, `/masks…`, `/logo` and `/idle/…` answer 404, clearing `props` or `masks` is refused (400), and `status.logo`, the feed's `props`, `looks` and `masks` hints and the `logo.changed` event are gone. `POST /api/v1/wallpaper` is in the logo's place, and `POST /api/v1/timers/{id}/show` shows a timer for the audience (below).
- **Tokens:** every request except pairing needs `Authorization: Bearer <token>`. There are no cookies, and a token is never put in a URL. The one address that carries something else is a media file's original for a `<video>` or an `<audio>`, which cannot send the header (Session 54): a link the device asks for with its token, signed for that device and that file alone, which stops working after 6 hours, when Drashti starts again, or at once when the device is removed.
- **Kinds of device:** a **Remote** may run the show as the operator window does (everything below but `GET /api/v1/stage` and the announcements): it reads the library and puts up and takes off what is in it by id, and since Session 54 views the playlists shared with phones and tablets and, while **Phones and tablets may add files** is on, adds a file of its own, imported as a dropped file is ("Files" below). A **Stage** device only reads the state, the stage screen's settings and (Session 51) the pictures its audience picture box draws (since Session 54 at the width it draws them). An **Announcements** device only sends announcements and reads what became of its own. Anything else a device asks is refused (`403`). Since Session 54 a Remote also sets up what the operator window sets up on its computer, through the same checks: the library's lists, the screens and Audience and Stage, video inputs and windows, the picture-in-picture box, the announcements' queue and MIDI, and since Session 55 the stage layout and a display's job ("The computer's screens" below). No device can change the sound, the stream, backups, the Access List or Drashti's other settings: those stay in Drashti's own window.
- **Simple Mode on the Drashti computer:** a Remote does only what its Simple Mode window does (`src/main/simple-mode-phones.ts`, with the window's own bounds). Since Session 57 (the owner's item 7) that is: open and change regular and smart playlists and folders (`playlists/new`, rename, delete and restore, with Undo; moving, renaming and removing rows, with Undo); play an item of any active non-template playlist, a slide that playlist plays, and Repeat Slides; Next/Back, clears/hides and Clear all, Put it back, Black-out, wallpapers, live zoom/Back to Whole; Pause, Play and moving what plays (`playing/…`); a video row's When it ends; and Audio, playing and changing audio playlists (`music/…`). Adding library files to a playlist (`playlists/{id}/add`), marker jumps, timer/message/lower-third puts, direct Media puts and setup are refused with 403. Until Session 57 a Remote was bounded by the playlist open in that window, with Play on paused content only. Reads remain available. A refused command returns `{"ok":false,"error":"forbidden","message":"…"}`. The phone’s explanation says what it does in Simple Mode (playlists, playback and Audio); with Pro access it names the computer’s way out of Simple Mode, and with Simple-only access it says that access is Simple Mode only, with no Pro route. The existing window refusal for Simple-only access is "Simple Mode is on, and this computer’s access is Simple Mode only, so this cannot be changed here." Files/photos remain allowed while adding is enabled, going to the end of the playlist open in that window in Simple Mode (a video or sound to Added from Phones while it is a Repeat Slides one, and everything there with none open).
- **Access** (Session 54, access by Gmail: `docs/access-setup.md`): Drashti works only on a computer that is let in. While it is not (at its lock screen, before it is let in, or once it has stopped: its access removed, its request rejected, this computer unknown to the list, its length ended, or no answer from the list for 15 days since Session 55, where about 2 minutes with none only brings a line in Drashti's window saying how long it keeps working), every request is refused, pairing and files too (a preview, a picture, an original or its link, a file a phone adds): `503`, "Drashti has stopped: its access was removed or could not be checked. Nothing works until it is let in again." The feed too: a new one is refused as it opens (`503`), and one open as Drashti stops is closed with `{"type":"bye","reason":"stopped"}`. What is still being sent is cut off at once (an original a phone plays), and a file a phone is adding ends `failed`. The pages themselves still load, and say plainly that Drashti has stopped; a device stays paired, and works again once Drashti is let in.
- **Answers** are JSON: `{"ok": true, …}`, or `{"ok": false, "message": "…"}` with an HTTP status (an action the show refuses says `error` too, a short code such as `no-picture`):

  | Status   | Meaning                                                                                                                                                                  |
  | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | 400      | The request is not right (a missing field, a slide that does not exist).                                                                                                 |
  | 401      | No token, or one Drashti does not know (the device was removed): "This device is not paired with Drashti. Pair it again from Phones and tablets in Drashti."             |
  | 403      | This kind of device may not do this, Simple Mode refuses it, adding files is off (Session 54), or the request came from outside the local network or another web page.   |
  | 404      | No such request, playlist, presentation, media item or lower third, or a file from a phone that Drashti no longer has.                                                   |
  | 405      | That request takes another method (actions are `POST`).                                                                                                                  |
  | 409      | The show cannot do it now (nothing is live, nothing to put back, nothing playing there, the picture zoomed no longer up), or a file's piece is not where Drashti has it. |
  | 411      | A file's piece without its length (Session 54).                                                                                                                          |
  | 413, 415 | The body is too large (16 KB at most; a playlists' restore, 48 KB, for a folder's 1,000 ids; a file a phone adds, 2 GB, and a piece of it, 8 MB), or is not JSON.        |
  | 421      | The Host header is not this computer's address.                                                                                                                          |
  | 429      | Too many requests (about 20 a second per device), too many wrong pairing codes, or too many announcements or files from this device waiting.                             |
  | 503      | Drashti is busy (a picture not made yet); try again. And every request while Drashti is not let in (Session 54, above).                                                  |
  | 507      | Not enough free space on Drashti's computer for a file a phone adds (Session 54).                                                                                        |

- **Actions** answer `{"ok": true, "changed": true, "rev": 42}`: `rev` is the engine state's revision after the action, which the state feed reaches too. Actions are `POST`, so a link or a browser's prefetch can never set one off. A body, when there is one, is JSON (`Content-Type: application/json`).

## A token for a script

Pair a **Remote** device in Drashti (Phones, then Pair a Remote device) and exchange the six-digit code (it works once, for two minutes) with `POST /api/v1/pair`, the one request that needs no token (five wrong codes a minute from one address, and every try is refused for the rest of the minute; after ten wrong tries in all the code stops working):

```sh
curl -s -X POST "$DRASHTI/api/v1/pair" -H 'Content-Type: application/json' -d '{"code":"123456"}'
# {"ok":true,"token":"…","device":{"name":"Remote 1","kind":"remote"}}
```

The token is shown this once; Drashti keeps only its hash. Keep it like a password. To take it away, remove the device in the Phones panel: it stops working at once.

## Reading

```sh
curl -s "$DRASHTI/api/v1/me" -H "Authorization: Bearer $TOKEN"
# {"ok":true,"device":{"name":"Remote 1","kind":"remote"}}

curl -s "$DRASHTI/api/v1/status" -H "Authorization: Bearer $TOKEN"
```

`GET /api/v1/status` (Remote, Stage) says where the show is, in short:

```json
{
  "ok": true,
  "status": {
    "live": {
      "presentationId": "…",
      "slideIndex": 2,
      "slideCount": 5,
      "playlist": { "playlistId": "…", "itemId": "…" },
      "onScreen": true
    },
    "blackout": false,
    "wallpaper": false,
    "canPutBack": false,
    "next": { "kind": "slide", "presentationId": "…", "slideIndex": 3 },
    "messages": [{ "id": "message:…", "text": "Car 12 please move" }],
    "ticker": [{ "id": "…", "text": "Placeholder: prasad in the hall after arti" }],
    "timers": [{ "id": "…", "name": "Sabha starts in", "kind": "countdown", "running": true }],
    "stageMessage": false,
    "repeating": { "playlistId": "…", "name": "Lobby pictures" }
  }
}
```

`next` is what Next puts up: the next slide (`{"kind": "slide", "presentationId", "slideIndex"}`), the next playlist item when it is a picture, video or sound (`{"kind": "media", "itemId", "label"}`) or, since Session 51, a video input (`{"kind": "input", "itemId", "label"}`), or `null` when nothing comes next.

`repeating` is a Repeat Slides playlist going round (Session 26d), or `null`. While it goes round, `live.presentationId` is `repeat:` and the playlist's id: its steps are its pictures and its presentations' slides, in order.

A step being made for another request is waited for. When one cannot be made now (too many waiting, less than 2 GB free on Drashti's disk, a file FFmpeg cannot read), the answer is 503: keep the picture had so far, and ask again in a moment; a step that could not be made is not tried again for 5 minutes (503 meanwhile). Answers carry an `ETag`, so asking again for one already had costs nothing.

## Running the show (Remote)

```sh
curl -s -X POST "$DRASHTI/api/v1/trigger/next" -H "Authorization: Bearer $TOKEN"
curl -s -X POST "$DRASHTI/api/v1/trigger/back" -H "Authorization: Bearer $TOKEN"
curl -s -X POST "$DRASHTI/api/v1/blackout"     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"on":true}'
curl -s -X POST "$DRASHTI/api/v1/clear/all"    -H "Authorization: Bearer $TOKEN"
```

Since Session 54 the phone remote mirrors the operator window, laid out for the phone: besides Next and Back, the slides and the clears (named with their keys, `GET /api/v1/keys`), it puts up and takes off the library's pictures, videos and sounds, the lower thirds, a timer for the audience (Session 55; a timer alone on the screens before) and the stage message, starts Repeat Slides going round, plays and pauses the audio playlists, and skips, moves, pauses and plays what plays. Each goes up or comes off as the operator window does it, and nothing here changes the library: a lower third or a media item is put up by its id, as Drashti reads it from the library, never sent whole.

## Files: shared playlists and adding from a phone (Remote)

Session 54. **Shared from Drashti:** a playlist the operator shares with phones and tablets (right-click it in Drashti, **Share with Phones and Tablets**; a folder playlist too) is listed here for Remote devices, to view and play on the device itself: its pictures and videos as any are (`GET /api/v1/media/{id}/picture` and `/original` above), and its sounds, whose originals are sent only while a shared playlist has them. It is read-only: nothing here changes it, and nothing here puts it on the screens (running the show goes through the playlist requests above, as before). Never for a Stage or Announcements device.

**Add from this Phone:** while **Phones and tablets may add files** is on in Drashti's Phones and tablets panel (off until someone turns it on, in Pro Mode; Simple Mode does not stop what comes while it is on), a Remote device may send a picture, video, sound, PDF, PowerPoint (`.pptx`; an older `.ppt` ends `failed`, its `message` saying to save it as `.pptx`) or Keynote file, up to 2 GB, whole and never shrunk. It never goes live by itself. **Add photos** (Session 55): a picture sent with `"into": "open"` goes instead to the end of the playlist open in Drashti's window in Pro Mode (an ordinary playlist: not a folder, template, smart or Repeat Slides one); with none open, or for anything but a picture, it goes to Added from Phones as any file does. `adding.openPlaylist` names that playlist. Drashti keeps 2 GB free on its disk, with the file and the import's copy of it in place. While the stream is on air or recording, the pieces are taken at about 2 MB a second, so the stream keeps its network; a PDF, PowerPoint or Keynote file, which its import converts, waits to be imported until the stream ends (its `message` says so meanwhile), and what Drashti cannot play is converted by itself afterwards, never on air.

## The state feed (WebSocket)

**Slide picture readiness.** The hall and the stream may retain the preceding painted slide while the new slide's pictures become drawable (at most 3 seconds); the state feed and its engine times already describe the new slide. When `picturesFirst` is enabled, successfully decoded addresses are recorded in the page by the Next preloader and slide waits; an encoded image marked `complete` still waits if that decode has not finished. A synchronous image preference guards against Chromium discarding an earlier decoded copy. A prepared Next retains its same-frame cut, and key/fill keeps its shared cut timing without the added decode wait or preference. The decode wait changes rendering without changing the engine times. A new hall or stream page gives its current images priority over Next preloads. That initial priority ends on a failed decode, a changed current picture or its own bound of 3 seconds; it adds no time to the existing display deadline. Key/fill bypasses that priority.

**Display copies of oversized still pictures.** A picture's ephemeral `pictures[id].display` gives the ready copy's `key`, `width` and `height`. The hall, stream and their preloads select that same source from their first decode. The source has only the pixels the largest configured physical display or stream needs, retaining the density a saved crop, turn or zoom needs; small pictures and animation keep their original. New picture imports, converted pictures and assets inside imported slides await this copy before they are admitted to the library. Work runs one job at a time in a separate process, with its actual OS priority checked below normal; older library pictures and larger screen demands wait for an idle show. The original media id, hash, original-role URL, editing, export and backup bytes stay the same. Display copies are private, regenerable files, excluded from backups and removed with their original. A Node requests the display file first and keeps the full descriptor for its download queue and saved state; only its output state temporarily uses an older original already cached locally until the display file arrives (owner Q60-48 A). A new item with neither local file still requests the small source first. This adds no frame, timer or delay to the existing 3-second display deadline or key/fill timing.

Paired devices keep their places when new devices are waiting. A new request may receive `503` with a plain busy message; wait before pairing another device. Pairing, tokens and the feed’s hello remain as described below.

`ws://<computer>:8740/api/v1/feed` (Remote and Stage devices). The first message must say who the device is, within five seconds:

```js
const ws = new WebSocket('ws://192.168.1.20:8740/api/v1/feed');
ws.onopen = () => ws.send(JSON.stringify({ type: 'hello', token }));
ws.onmessage = (e) => {
  const m = JSON.parse(e.data);
  // {type:'welcome', device}, then {type:'engine', message: {kind:'snapshot', rev, state, …}},
  // then each change as {type:'engine', message: {kind:'patch', baseRev, rev, ops}}.
};
```

## OSC control over UDP

OSC is independent of HTTP and Phones: no HTTP token or pairing is used. It is off by default. An admin opens **OSC control…** (its section under LIVE, or **Tools › OSC Control…**) in desktop Pro Mode, lists trusted local IPv4 sender addresses, selects a UDP port (9000 by default; 1024–65535), then enables and saves it. Initially only `127.0.0.1` is listed. Only those exact addresses may send; no hostnames, ranges, public addresses or discovery. With loopback senders only, the socket binds `127.0.0.1`; otherwise `0.0.0.0`, still filtering every sender. A busy port fails visibly and never falls back to another port. Disable, settings changes and quit close the socket and cancel waiting bundles. Explicit enable is remembered across restarts. Access removal closes the socket too; access returning resumes it only if enabled.

**Security and delivery.** OSC has no password, authentication or encryption. Source addresses can be impersonated. Use a trusted private network and its firewall; never forward the UDP port. Drashti sends no OSC replies, state, slide words or timer readings. UDP may lose, reorder or repeat a packet, so prefer explicit on/off values over a toggle when a sender may send again. The actions below enter the API's existing action layer, retaining its validation, Drashti access checks and Simple Mode rules; a refused action does nothing. There is no raw-command endpoint. Library edits, streaming, screen setup, mode and settings are unavailable. Macros were removed from Drashti; macro addresses are rejected.

**Addresses and arguments.** Send one literal address below. Patterns and wildcards are rejected. `s` is an OSC string, `i` a 32-bit integer. An on/off argument accepts `i` or `f` equal to 0 or 1, or OSC `T`/`F`. No extra arguments are accepted.

For Companion, select an OSC connection targeting this computer's address and chosen UDP port, then create buttons with the literal addresses and typed arguments above.

**Packet limits.** The reader follows the [OSC 1.0 wire format](https://opensoundcontrol.stanford.edu/spec-1_0.html), including messages, nested bundles and type tags. It reads `i f s b` and the optional `h t d S c r m T F N I` and arrays; actions accept only the argument types described above. Unknown types, bad padding, truncated values, non-ASCII strings and non-finite numeric values are rejected. Every datagram is at most 16 KiB, nesting at most 8, at most 32 messages, 64 arguments per message and 256 arguments in all. An entire packet is parsed and mapped before any part runs: malformed data or an unknown address causes no partial action. A bundle is an ordered series of existing actions, not a transaction that rolls earlier actions back if a later action is refused by the show.

Immediate timetag `1` and past tags run now. NTP future tags may be at most one minute ahead, with at most 64 messages waiting across all senders; farther times or a full queue refuse the whole packet. Nested bundle tags cannot precede their parent. Future actions recheck access and sender membership when due. No scheduled action survives disable, reconfiguration, access removal or quit.

Before parsing, ingress is limited to 50 packets/second with burst 200 overall, including malformed packets from listed senders. Each sender is limited as an API device is: 20 actions/second, burst 40; overall, 40 actions/second, burst 80. Every message in a bundle spends an action allowance before any part runs. These action limits apply at receipt and again at execution, so waiting bundles cannot add another burst when they become due. An over-budget packet (or timed group at execution) is dropped as a whole, with no reply. Settings show counts; logs contain fixed lifecycle and action names only, never sender addresses, arguments or packet content.

## Events out (webhooks)

The other way round (Session 28): Drashti **sends** a signed `POST` to each address added under **File › Events Out…** (Pro Mode), for the kinds ticked there. Nothing is on until then. An address must be on this computer or the local network, unless it is the one `https` address on the internet the dialog allows. A receiver needs nothing from the API above: no token, no pairing. In the desktop dialog, **Copy** beside a newly shown secret puts it on the clipboard and says **Copied**; paste it into the receiver before **Done**. **New secret** makes a replacement; the old one signs too for a day. See the [Manual's Events out steps](manual/settings.md#events-out).

**The body** is JSON:

```json
{
  "type": "slide.changed",
  "timestamp": "2026-10-16T19:30:05.123Z",
  "data": {
    "presentationId": "…",
    "slideIndex": 2,
    "slideCount": 5,
    "playlistId": "…",
    "itemId": "…",
    "repeat": false
  }
}
```

| `type`                                                   | `data`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `slide.changed`                                          | `presentationId`, `slideIndex`, `slideCount`, `playlistId`, `itemId` (null when not from a playlist), `repeat` (true when a Repeat Slides playlist moved on by itself). **Words** come only where **Include the words** is ticked for that kind at that address: `text` for `slide.changed` (the slide's lines, all its languages, one to a line, 200 characters at most; on a slide from a PowerPoint deck that Drashti plays itself, only those on the screens by the end of the click showing) and `announcement.waiting`, `name` for `screen.stopped` and `screen.showing`. **The headers:**

| Header                    | Holds                                                                                                                                                                                                    |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webhook-id`              | The event's id (`msg_…`): the same on every try, so a receiver that sees it twice can drop the second.                                                                                                   |
| `webhook-timestamp`       | When this try was sent, in seconds since 1970.                                                                                                                                                           |
| `webhook-signature`       | `v1,` and the base64 HMAC-SHA256 of `id.timestamp.body`, keyed by the secret's bytes ([Standard Webhooks](https://www.standardwebhooks.com)). For a day after **New secret**, two, separated by a space. |
| `X-Drashti-Signature-256` | `sha256=` and the hex HMAC-SHA256 of the body, keyed by the whole secret as shown (`whsec_…`), as GitHub signs its webhooks: for a receiver that can only make a plain HMAC.                             |
| `X-Drashti-Event`         | The `type`, again.                                                                                                                                                                                       |

**Checking one**, in Node (a Standard Webhooks library does the first for you):

```js
import { createHmac, timingSafeEqual } from 'node:crypto';

const same = (a, b) => a.length === b.length && timingSafeEqual(Buffer.from(a), Buffer.from(b));

/** `body` exactly as it arrived, before any JSON parsing. */
function fromDrashti(secret, headers, body) {
  const id = headers['webhook-id'];
  const ts = headers['webhook-timestamp'];
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false; // more than 5 minutes off
  const key = Buffer.from(secret.replace(/^whsec_/, ''), 'base64');
  const want = `v1,${createHmac('sha256', key).update(`${id}.${ts}.${body}`).digest('base64')}`;
  return headers['webhook-signature'].split(' ').some((s) => same(s, want));
}

/** Or the plain one. */
const githubStyle = (secret, headers, body) =>
  same(
    headers['x-drashti-signature-256'],
    `sha256=${createHmac('sha256', secret).update(body).digest('hex')}`,
  );
```

In n8n, the **Crypto** node's HMAC (SHA256, hex, the secret as shown) of the body as it arrived, with `sha256=` before it, should equal `X-Drashti-Signature-256`.

**Answering.** Answer `2xx` quickly (within 15 seconds; the body is not read). Anything else is tried again: at once, then after 5 s, 30 s, 2 min, 10 min and 30 min, and then the event is given up (the dialog counts those). Events to one address go one at a time, in order; slide changes within 250 ms of each other go as the last one. A `410` turns the address off until it is turned on again in the dialog; a `404`, a redirect (never followed) or another `4xx` means the address is set up wrongly, and is tried only twice more. Events waiting when Drashti quits are not sent later.

Live captions (state 26, retained by state 27) are never sent in this API, to a phone or to a node; captions are left out or null.

## Video analysis (operator IPC)

`media.videoAnalysis(mediaId, audioStream = 0, retry = false)` returns a snapshot of source-time waveform peaks, scene suggestions and a bounded JPEG contact sheet. `audioStream` is the source's zero-based audio ordinal (`0:a:N`); `null` explicitly requests no sound. The Edit Video recipe's default `audioTrack: null` therefore maps to ordinal 0. Only the operator window may ask. There is no HTTP/OSC command and no live-engine action.

`Waveform` and `SceneSuggestions` are operator components under `renderer/src/video-analysis`. ## Video playing copies and exports (operator IPC)

`media.proxyStatus(mediaId, retry = false)` returns a `VideoProxyResult`; `media.stopProxy(mediaId)` stops its accepted request. Status distinguishes checking, waiting, preparing, ready, not-needed, failed and stopped, including progress and the immutable ready media ID. Automatic work is limited to oversized video on at most two logical cores or software compositing/video decode. Copies fit within 1920 × 1080 or portrait 1080 × 1920, normalize sample aspect and orientation, and preserve alpha in WebM. `ProxyService.readyFor(id)` is consumed once at the new-showing boundary; `sourceOf(id)` follows the immutable ID back to its source rendition. No ready URL is replaced while playing.

`media.clipExport({mediaId,startMs,endMs,frame:'original'|'edited',shape:'source'|'vertical',container:'mp4'|'webm',addToLibrary,revision})` is strict, operator/Pro-only. Times are original source milliseconds. The native Save as… dialog supplies the destination, never the page. Edited requests carry the saved revision and use S2's pure original-source render planner, baking effects and time mapping exactly once. Original requests use an accurate decoded cut. A reduced proxy is never an export input. Vertical output is a central 1080 × 1920 crop. MP4 refuses alpha with a request to choose WebM.

`media.clipExports()`, `media.stopClipExport(jobId)` and `media.showClipExport(jobId)` read progress, stop a pending export or reveal a completed file. A cancelled Save as… returns `{ok:true,job:null}`. Accepted requests persist across editor close and restart; resume checks captured source and recipe identities. One worker covers header reads, encoding, validation and abortable hashing/copy registration. All jobs require idle show/stream/recording gates and verified below-normal OS priority; activity removes partials and restarts from the beginning. An existing destination is preserved by choosing a free name. Completed optional imports become listed only after validation and file publication. These calls add no HTTP command or live-engine action.

`media.combineVideos({mediaIds,transition:'dissolve'|'fade-black'|'cut',transitionMs,saveCopy})` (alpha.22, Combine videos…) is strict, operator/Pro-only: two to ten distinct Media video IDs, in the order they play, and a transition of 500 to 3000 ms. Main resolves each to its own Media file (never a path from the page) and queues one job in the same idle worker: every chosen file is read there first, then one FFmpeg run with one `-i` per chosen file (`-protocol_whitelist file`, never the concat protocol or a list file) joins them: each fitted inside the first video's upright, square-pixel size (letterboxed, at most the H.264 size Drashti draws everywhere) at its frame rate (at most 60), sound resampled to 48 kHz stereo and a silent track for a video without sound; then at each join `xfade` (`fade` for Dissolve, `fadeblack` for Fade through black) with `acrossfade` (`tri` curves, or `exp` so the sound dips), or the `concat` filter for Cut and for a join where a video is shorter than the transition (the job's `short` names them). H.264 + AAC in MP4, its length the sum less each transition. The output is checked (picture size, sound, length within 250 ms), copied into Media and listed only then; the originals are only read. A combine failing or stopped after that copy (a chosen video changed, the listing refused, a wait or Stop at that moment, Drashti closing) removes the unlisted row and its file (`discardUnlisted`: only rows made from that combine's own work file; never a listed row, never a row anything uses (`mediaInUse`, the Trim cleanup's checks: an import may take a row up by its bytes), and never a file another row keeps; a row goes only with its file, so one that cannot be removed is tried again at the next start), and only at a quiet moment: nothing playing, off air, not recording, and no import or deck preparation going (either can take up a file or a row by its bytes); otherwise it is left for the next start's sweep, which keeps to the same rule. A wait just after that copy removes it as the next attempt begins, before it copies again; what a quit or a crash left is removed at the next start. A chosen video changed or gone meanwhile fails the job with that video's own words. `saveCopy` opens the system's save dialog first (Downloads, the new video's name; cancelled: `{ok:true,job:null}`, nothing queued) and, once done, copies Media's new file there with Export…'s own helper (`exportMediaFile`, never over a file already there: a free name beside it). `media.combineList()` returns each `CombineJob` (waiting, preparing, done with the new `mediaId` and `savedTo`, failed or stopped, with progress and words); `media.stopCombine(jobId)` stops one waiting or going, leaving nothing. Its window's **Export…** is `media.exportFile(mediaId)` on the new video. A combine waits as an export the operator asked for does (`waitForPlaying`: a video or sound playing, the stream on air, a recording; never a still slide, a picture or the Wallpaper). Combines are not kept across a restart. These calls add no HTTP command or live-engine action; Simple Mode refuses combining and stopping.

Edit Video’s prepared IDs retain immutable recipe history. Main resolves source-owned tone, captions, resume points and play counts through that history; source times are mapped once for the prepared file. The pure `editPlan` accepts a source-time export interval inside the recipe trim and an optional frame/fit override, always reading the source rather than a proxy.

## Idle video preparation worker

`ConvertService.saveCopy` also prepares video-edit assets through the existing single worker. These callers set `waitForShow: true` and `strictPriority: true`. ## Native Gujarati/Hindi recogniser (main process only)

`createIndicEngine` implements `SpeechEngine`, selected only by the caption integration’s explicit model choice.
`acquire(language, signal)` obtains and holds cap-pack’s checked model through native process exit; `routeCFiles`
accepts only `indicconformer-ctc-onnx-v1`, exactly one purpose (`captions-gu` or `captions-hi`), with `model.onnx`, `tokens.txt` and
`frontend.bin`. The graph takes `[1,80,T]` float features and `[1]` int64 length; its first output is `[1,T/4,257]`
float language-masked CTC scores (blank 256). Tokens are 256 UTF-8 pieces and `<blank>` last; the front end is
80 × 257 little-endian float32 Slaney mel weights, matching the export. No Python or model-supplied code runs.

`ic-ctc --pcm-serve` reads private stdin frames: uint32 little-endian PCM byte count (positive, even, at most
384,000) then that many mono 16 kHz signed-16 little-endian bytes. It reports readiness with protocolVersion 1, sampleRate 16000, channels 1 and sampleFormat s16le, then one bounded
UTF-8 JSON line per clip: language, text, words (`w`, start/end seconds), coarse 40 ms timing, null confidence and
aggregate durations. Each word also has `c`, the mean over its CTC frames of the top token's posterior (0-1; the
reply-level `confidence` stays null). Main alone maps sample offsets to capture times. A reply whose every word is
one syllable (one letter or digit with its vowel signs) AND below `NOISE_CONFIDENCE` (0.5) is noise or hum
(`noiseOnly`): a growing phrase is sent empty, a whole one is dropped; a reply without `c` is never called noise. There is one decode in flight, at most two
queued finals; a stopped session kills the helper and discards its replies. Readiness is bounded by 90 seconds,
no answer by 8 seconds terminates the helper; normal lag/rest guards remain. No PCM files, sockets or text logs.

Build each target on its own system with `scripts/fetch-indic.mjs` (pinned Microsoft release, exact size and SHA-256),
or build locally against an already verified extraction with `scripts/build-indic.mjs` and `DRASHTI_ORT_ROOT` /
`DRASHTI_INDIC_OUT`. Local linked `vendor` destinations are refused. `findIndic` locates the bundled helper; models
stay in cap-pack’s per-computer store. Runtime notices ship with the helper and under `licenses/onnxruntime/`.

`indicProblem(platform, systemVersion)` checks this runtime’s actual macOS 13.4 minimum; pass it as the recogniser’s
`problem()` preflight so older Macs get a plain reason before loading a model. Production startup uses `--admit`: the
helper waits for the private four bytes `GO01` before model loading, sent only after background priority is set.

`workGate { allowed(), listen(changed) }` is Main’s read-only authoritative background-work lease for protected mode. Without it,
or while it is closed/unknown, the recogniser loads no model and performs no inference. Revocation cancels native
compute immediately without awaiting exit and invalidates pending results; a later opening starts fresh. For protected mode the main
integration must adapt L8’s public signal, never infer permission from an elapsed timer. Tests provide an explicit
stand-in gate. The ordinary Whisper path is outside this new engine and remains unchanged.

`createIndicRoute({ store, ...engineOptions })` directly matches cap-integration’s `CaptionRoute.make(model, language)`.
It matches the selected reference to full checked metadata through `store.model`, pins the model-file SHA-256s, then obtains a fresh hold through
`store.acquire` at start. Changed identity or purpose releases the hold without starting native work. The resolver
accepts the shared language type and returns null for every language other than Gujarati or Hindi.

Main may explicitly select `admission: 'below-show'` for continuous ASR under the integration’s scheduling policy.
This does not bypass native priority admission or any lag, queue, model, generation or cancellation guard. If a
`workGate` is supplied it remains authoritative, including when closed or broken. With neither explicit admission
nor a gate the recogniser stays closed. Main/lead owns the ASR policy choice; translation’s lease is separate.

Phrases carry the speech hub’s ids, `s1, s2…` in each listening, as Whisper’s engine gives them; the hub turns any
other id away. `ic-ctc --runtime`, alone, starts ONNX Runtime beside the helper without any model and prints
`{"runtime":"1.23.2","api":23}`. The packaged self-test (`DRASHTI_SELFTEST=ffmpeg`, `scripts/check-ffmpeg.mjs
--packaged`, `scripts/check-installers.mjs`) requires that answer, with the runtime’s libraries beside the helper (on
Windows its two DLLs and the app-local Microsoft runtime).

**Prepare translations' engine (alpha.22).** The editor's bridge (`slideEditor`) has `translationStatus(from, to)` (`{ installed, available, message }`), `translationDraft({ source, from, to })` (`{ ok: true, text }` or `{ ok: false, message, thisBoxOnly? }`) and `translationCancel()`. Main answers them in Pro Mode only (Simple Mode's lock refuses them), from the operator or the editor window, and only off air (not streaming or recording); a source is at most 20,000 characters, each line translated on its own. The engine (`src/main/translation/`) runs `drashti-translate`, a separate program (`tools/translate/drashti-translate.cc`, built by `scripts/fetch-translate.mjs`) that reads one JSON object a line on standard input (`load`, `translate`, `pieces`, `cancel`, `unload`, `quit`) and answers one a line, protocol 1; it opens no port. Its text pipeline is a port of IndicTransToolkit 1.1.1 with indic-nlp-library 0.92 and sacremoses 0.2.0, checked against their output (`tests/fixtures/translation/`). It uses an imported pack's model of format `indictrans2-ct2-int8` (`model.bin`, `config.json`, `source_vocabulary.json`, `target_vocabulary.json`, `source.spm`) for the purpose `translation-<from>-<to>`. A draft is returned to the dialog only and saved like hand-written words: unchecked.

## Caption and translation model packs (desktop)

Since alpha.22 an admin imports an offline model pack with **Help › Caption and Translation Models…** (Pro Mode; the admin's guide, section 32). There is no HTTP route, and nothing is ever fetched. The operator window's bridge `modelPacks` offers `view()`, `import('folder' | 'zip')` (main's own open dialog chooses the path; the page never gives one), `cancel()`, `remove(packId)`, `licence(packId, file)` and `onChanged(listener)`; only the operator window may ask, and Simple Mode refuses all of them.

**The pack's list.** `drashti-model-pack.json`, at the top of the pack's folder or zip (or of the one folder a zip holds), is `{ "format": "drashti-model-pack", "version": 1, "id", "name", "release", "files": [...] }`. `id` is 1-64 lower-case letters, digits and `-`; `release` is the pack's own version. Each file is `{ "name", "bytes", "sha256", "licence", "purpose": [...] }`. `name` is a path inside the pack by `/`, each part starting with a letter, a digit or `_`. `licence` is one of `MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `CC0-1.0` or `CC-BY-4.0`. `purpose` is `["licence"]` for a licence's own text, or one or more of `captions-gu`, `captions-hi`, `captions-en` and `translation-<from>-<to>` (two different languages of `gu`, `hi` and `en`). A model's file also has `"model"` (its id, the same rules as the pack's), `"format"` (the engine's, such as `whisper-ggml` or `ctranslate2`), `"licenceFile"` (the name of a licence text in the pack) and `"attribution"` (up to 300 characters: who made it and where it is from, as its licence asks; the dialog shows it). `scripts/make-model-pack.mjs <folder> <plan.json>` writes the list from a plan and the files themselves. All of a model's files share its purposes and format, and each model's files sit in a folder of their own: its folder is where an engine is pointed. Up to 1,000 files, each name once in any letter case. Anything wrong refuses the whole pack before anything is copied; a file whose bytes or SHA-256 do not match refuses it as it is copied, and nothing is kept.

**For a caption or translation engine** (main process; `src/main/model-packs/store.ts`). `ModelPackStore.model(id)` gives the installed, whole model (`{ id, packId, packName, packRelease, purposes, format, folder, files: [{ name, path, bytes, sha256, licence }], licences, attributions }`) or `null`; `forPurpose(purpose)` gives every such model for a purpose, the newest import first. Both check only that each file is there at its checked size. Before loading, call `acquire(id, signal?)`: it checks every file's SHA-256 again (once a run, and again if a file changed since), and holds the copy until `release()`. While held, a pack is never removed, and a newer copy replaces it only for later `acquire` calls; the held folder stays whole until it is let go. `null` means not installed or not whole: the dialog then says a file changed and asks for the pack to be imported again. A pack never runs anything: its files are data, readable by this computer's user only.
